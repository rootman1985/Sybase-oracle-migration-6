# Sybase ASE -> Oracle Migrator

Java 17 tool designed for large Sybase ASE to Oracle migrations.

## Design

The program does NOT discover source/target column metadata from the databases.

You provide the migration contract in one CSV:

`src/main/resources/column-mappings.csv`

Each row contains:

- source catalog/database
- source schema
- source table
- source column
- source type
- target schema
- target table
- target column
- target type

Precision, scale and lengths are intentionally not part of the input file.
The target Oracle schema is assumed to already have the desired precision/scale/length.

The FIRST source column of each table is automatically used as the chunk/key column.

## CSV format

```csv
sourceCatalog,sourceSchema,sourceTable,sourceColumn,sourceType,targetSchema,targetTable,targetColumn,targetType
CDXHisto,dbo,CDX_HST_AUTOMATE_LOG,idDocument,int,REPORTING,TEST_OROUDA NE_LOG,IDDOCUMENT,NUMBER
```

Remove spaces from identifiers; the example above is illustrative.

Example:

```csv
sourceCatalog,sourceSchema,sourceTable,sourceColumn,sourceType,targetSchema,targetTable,targetColumn,targetType
CDXHisto,dbo,CDX_HST_AUTOMATE_LOG,idDocument,int,REPORTING,TEST_OROUDANE_LOG,IDDOCUMENT,NUMBER
CDXHisto,dbo,CDX_HST_AUTOMATE_LOG,idVault,int,REPORTING,TEST_OROUDANE_LOG,IDVAULT,NUMBER
CDXHisto,dbo,CDX_HST_AUTOMATE_LOG,id2Sdoc,varchar,REPORTING,TEST_OROUDANE_LOG,ID2SDOC,VARCHAR2
CDXHisto,dbo,CDX_HST_AUTOMATE_LOG,success,tinyint,REPORTING,TEST_OROUDANE_LOG,SUCCESS,NUMBER
CDXHisto,dbo,CDX_HST_AUTOMATE_LOG,error,varchar,REPORTING,TEST_OROUDANE_LOG,ERROR,VARCHAR2
CDXHisto,dbo,CDX_HST_AUTOMATE_LOG,params,text,REPORTING,TEST_OROUDANE_LOG,PARAMS,CLOB
CDXHisto,dbo,CDX_HST_AUTOMATE_LOG,dateLog,datetime,REPORTING,TEST_OROUDANE_LOG,DATELOG,TIMESTAMP
```

Special Sybase ASE timestamp example:

```csv
CDXHisto,dbo,MY_TABLE,ts_col,timestamp,REPORTING,MY_TABLE,TS_COL,RAW
```

This means:

`Sybase ASE timestamp -> Oracle RAW(8)`

The program reads it with `ResultSet.getBytes()` and checks that it is exactly 8 bytes.

## Properties

Edit:

`src/main/resources/application.properties`

Set the Sybase and Oracle URLs/user/password and batch sizes.

For Sybase, the URL does not contain the database name because the database/catalog is supplied by each CSV row and selected with `Connection.setCatalog()`.

## CHECK mode

Validates:

- source/target table groups
- duplicate columns
- first source column as key
- supported source/target type combinations
- required target/source mapping structure

It does not migrate data.

## MIGRATE mode

Run after CHECK is successful.

The source is read with keyset pagination:

`WHERE first_source_column > ? ORDER BY first_source_column`

and a JDBC maximum row count for each batch.

Rows are inserted into Oracle using JDBC batch inserts and commits.

## Commands

From IntelliJ, run `MigrationApplication`.

Or:

```text
java -cp ... fr.migration.MigrationApplication CHECK
java -cp ... fr.migration.MigrationApplication MIGRATE
```

The project also contains Windows scripts.

## Important

The program assumes the target Oracle table already exists with the desired precision/scale/length.

If the target column is an Oracle identity column, the CSV controls whether that identity column is explicitly inserted. If the identity is `GENERATED BY DEFAULT`, explicit source IDs are allowed. `GENERATED ALWAYS` normally requires a different strategy.

## Streaming edition with original 9-field CSV
`column-mappings.csv` is the ONLY table/column configuration. Each row has:
`sourceCatalog,sourceSchema,sourceTable,sourceColumn,sourceType,targetSchema,targetTable,targetColumn,targetType`.
Source catalog is selected using `Connection.setCatalog`; Oracle has no catalog field.
`CHECK` prints mapping structure; `MIGRATE` streams the Sybase SELECT without pagination and logs per-table row count, duration and errors in `logs/migration-tables-summary.csv`, and total duration in `logs/migration-run-summary.txt`.
Rows are committed every `migration.oracleJdbcBatchSize` rows. Previously committed rows remain if a table fails. Clear or reconcile target tables before rerunning. Stop source writes or use an appropriate consistent snapshot for exact counts. Verify Sybase jConnect server-side cursor/fetch behavior for memory-safe streaming. Test large LOBs carefully with JDBC batching.

## Adaptation performance et colonnes TEXT

- Les colonnes source `text`, `unitext` et `ntext` sont lues comme `String` et insérées vers `CLOB`/`NCLOB` via un `StringReader`, ou vers `VARCHAR2`/`CHAR` via `setString`. Cela préserve les `NULL` et évite de conserver un flux JDBC lié au `ResultSet` jusqu'à l'exécution du batch.
- Les colonnes `image`/`binary`/`varbinary` sont lues en octets; `timestamp` Sybase ASE reste un rowversion binaire de 8 octets et doit cibler Oracle `RAW(8)`.
- Les logs par table indiquent les lignes lues, les lignes validées, le temps passé dans `ResultSet.next()`, le temps d'exécution des lots d'insertion, le temps des commits et la durée totale. Les mesures `rs.next()` ne comprennent pas toutes les conversions de colonnes; elles servent à repérer les tendances, pas à constituer un profilage JDBC exhaustif.
- Les données `TEXT` sont temporairement matérialisées en `String` par ligne. Pour des valeurs très volumineuses, une stratégie LOB dédiée sans batch est préférable. Le comportement de streaming/fetch côté Sybase dépend aussi de la configuration du pilote jConnect.
